# Инструкция по размещению проектов на Mac mini

Обновлено: 9 октября 2026 года, Asia/Almaty. Инструкция для владельца, его коллег и чатов с инструментами разработки. Здесь опубликованы правила работы; адрес подключения и персональный доступ владелец передаёт отдельно.

## Что уже работает

- Mac mini M4, 10 физических ядер, 16 GiB памяти. Серверная среда — Ubuntu ARM64 в VM `seoweb-server`, Docker и Compose. VM выделено 10 vCPU, 10 GiB RAM и 150 GiB виртуального диска. CPU используется совместно с macOS; 6 GiB памяти оставлены хосту. Sparse-диск занимает физическое место по мере записи; свободное место перед деплоем проверять внутри Linux и на Mac.
- Linux и Docker запускаются при загрузке Mac до входа в рабочий стол. SSH работает независимо от рабочего стола.
- Внешний SSH — TCP **22022**, вход по персональным ключам. Транспорт и вход оператора с отдельного устройства проверены.
- Внешние TCP **80/443** доступны; общий Caddy обслуживает размещённые проекты с действительным HTTPS. Новые домены подключать к существующему ingress, сохраняя текущие маршруты и сертификаты.
- Ежедневный зашифрованный backup серверных данных на Google Диск около **03:00 Asia/Almaty**, с задержкой до 10 минут. Общая служба проверена 9 октября: успешная копия 23 контейнеров и 20 образов, без остановки сайтов. Временные native файлы заняли около 4,63 GiB; снимки всех текущих баз и объектов реально восстановлены в отдельных тестовых ресурсах.
- Владелец подключил статический публичный IPv4 у провайдера; новый адрес проверен. Конкретный endpoint передаётся отдельно. При последующей смене адреса потребуется обновить DNS и адрес SSH.

Для работы через выбранную схему не требуется устанавливать Tailscale/NetBird или переносить домены в Cloudflare. Сервер — один узел; мощность и backup не дают автоматического переключения при сбое питания или интернета.

## Работа с чата на серверном Mac

Папка инфраструктуры: `~/Desktop/CODEX/SERVER`. Перед любыми изменениями читать локальные инструкции и актуальное состояние: они могут быть новее этой публичной страницы.

```sh
cd ~/Desktop/CODEX/SERVER
./scripts/serverctl status
./scripts/serverctl docker ps
./scripts/serverctl shell
```

Последняя команда открывает Linux shell. Использовать существующие wrappers; внутренний SSH-порт Lima меняется при запуске. Вторую VM или второй Docker на Mac для очередного проекта создавать не нужно.

Локальная проверочная платформа: `http://127.0.0.1:8080/`, API readiness: `http://127.0.0.1:8080/api/health/ready`. Эти пути относятся к demo, не к новому приложению. Demo API без аутентификации не подключать к публичному ingress.

## Коллега или чат с другого компьютера

1. На своём устройстве создать отдельный SSH-ключ. Владельцу передать **только публичный файл `.pub`**, требуемое имя пользователя и назначение доступа. Приватный ключ остаётся на этом устройстве.
2. Владелец регистрирует именованного оператора и отдельно сообщает текущий публичный IPv4, порт 22022 и ожидаемый SSH host fingerprint.
3. Сравнить fingerprint перед первым принятием ключа сервера и подключиться своим ключом:

```sh
ssh -i ~/.ssh/macmini_operator -o IdentitiesOnly=yes -p 22022 OPERATOR@PUBLIC_IPV4
```

`OPERATOR`, `PUBLIC_IPV4` и путь к своему ключу заменить реальными значениями. Здесь нет общего пароля или общего приватного ключа.

Команда владельца на Mac для добавления **доверенного администратора**:

```sh
cd ~/Desktop/CODEX/SERVER
./scripts/serverctl shell sudo /usr/bin/python3 /srv/server/deployment/scripts/access/server-access.py add-admin OPERATOR --public-key-file - < /path/to/operator.pub
```

Текущая роль администратора имеет полный sudo/Docker доступ ко всем проектам в этой VM. Это не изолированный аккаунт клиента. Список и отзыв доступа описаны в локальном `docs/SSH_ACCESS.md`.

Обычный браузерный чат без SSH/локальных инструментов не сможет развернуть проект только по ссылке. Пароль Google, PIN удалённого рабочего стола, OAuth tokens, приватные SSH-ключи и ключ backup передавать ему не требуется.

## Размещение нового проекта

1. Проверить стек и совместимость сборки с `linux/arm64`. Статический React-сайт может раздаваться как готовые файлы; приложению с серверным рендерингом или API нужен отдельный процесс/контейнер.
2. Исходники хранить в репозитории самого проекта; рабочие файлы на Linux — в `/srv/server/projects/PROJECT_ID`. Для каждого проекта использовать отдельное Compose project name, сети и volumes.
3. Секреты хранить вне Git: `/srv/server/secrets/PROJECT_ID` либо `/srv/server-secrets/PROJECT_ID`. Uploads и постоянные данные размещать в серверных каталогах или Docker local volumes. Базы данных не открывать публичными host-портами.
4. Подготовить повторяемый release, healthchecks и возврат предыдущего релиза. Перед миграциями БД отдельно продумать восстановление данных: откат image сам по себе миграцию не отменяет.
5. Проверить сборку, страницы/404, API/DB readiness, сохранность данных после перезапуска и восстановление из backup. Зафиксировать команды и результаты в документации проекта.

`/srv/server/deployment` — каталог общей платформы. Существующий `scripts/deploy-local.sh` обновляет платформу и demo; это не универсальный загрузчик произвольного приложения. Общий ingress и backup меняет один координатор, чтобы чаты не перезаписывали настройки друг друга.

## Домен и HTTPS

Все проекты могут использовать один публичный IP: общий Caddy выбирает приложение по домену.

1. Владелец выбирает конкретный hostname. Подготовить проект и правила общего public Caddy, постоянный volume сертификатов и backend без публичного порта БД.
2. У существующего DNS-провайдера направить запись `A` выбранного hostname на актуальный публичный IPv4 сервера. Почтовые и посторонние записи сохранить. `AAAA` добавлять только при реально настроенном публичном IPv6.
3. Добавить выбранный hostname/backend в существующий `/srv/server/deployment/platform/public-ingress/Caddyfile`. Перед применением проверить Caddy-конфигурацию; сохранить текущие маршруты, общий Compose project и постоянный volume сертификатов. Второй контейнер на тех же портах не запускать.
4. Применить подготовленное изменение общего ingress и проверить DNS, HTTP/HTTPS, сертификат, страницы и API с независимой сети.

Если провайдер закрепит другой статический IPv4, проверить новый адрес и обновить DNS/SSH endpoint; пересоздавать сервер не требуется.

## Автоматические резервные копии

Общий backup в режиме `online-server-v3` включает серверные каталоги `/srv/server`, `/srv/server-secrets`, `/opt/server`, обычные Docker local volumes, конфигурацию Linux и образы приложений. PostgreSQL сохраняется штатными сжатыми dumps вместе с ролями, SQLite — через Online Backup API, Redis — как native RDB, MinIO — через S3 с настройками бакетов и IAM. Сырые работающие файлы баз исключены из обычного копирования.

Сайты продолжают работать во время backup. Обычные файлы отправляются напрямую в зашифрованный restic repository, уникальные Docker images — потоком с проверенными ссылками для восстановления. Большая временная копия всех контейнеров больше не строится; локально остаются native artifacts баз и объектов. Сохраняется резерв не менее 5 GiB. Независимые online snapshots разных БД и файлов не образуют одну общую транзакцию: связь записей и загруженных файлов проверяется для каждого проекта отдельно. Ежедневная копия допускает потерю изменений до суток; PITR не настроен.

Новые БД, неизвестные persistent writable layers, remote volumes и bind mounts вне серверных каталогов требуют проверенного backup adapter до размещения. Проверка отказывает, если данные нельзя безопасно восстановить; она не должна молча исключать новый datastore. Настройки PostgreSQL и Redis, включая роли/ACL, HBA и используемые конфигурационные файлы, сохраняются вместе с native данными. Постоянные данные приложения хранить в managed каталоге или volume, код — в воспроизводимом release/image. Это backup серверных данных, не образ всего Mac.

Во время общей операции не пересоздавать контейнеры/volumes и не менять общий ingress: backup и deploy сериализуются через `/var/lib/server-backup/operation.lock`. Для проверки места использовать канонический вызов внутри Linux:

```sh
sudo env BACKUP_CONFIG=/etc/server-backup/offsite.conf \
  /srv/server/deployment/scripts/backup/server-backup.sh capacity-preflight
```

Он возвращает JSON с `kind=online-server-v3`, `format_version=3`, native `estimated_capture_bytes` и `reserve_bytes=5368709120`. Требовать свободное место под native estimate, резерв и собственный запас проекта. Старый `capture-server.py --capacity-preflight` продолжает описывать cold v2; его не вызывать как проверку новой схемы. Если caller уже держит общий lock, передать тот же FD через `BACKUP_OPERATION_LOCK_FD=N` и `pass_fds`; повторный независимый flock будет конфликтовать. Старые SHA-pinned проектные runners переводить новой проверенной версией, сохраняя WAL/free-space/approval guards.

Для v3 выбрать завершённое поколение из `snapshots`, проверить `verify-online`, восстановить `restore-online-native` или `restore-online` в **новый** защищённый каталог. Старый `restore-files` не собирает полный комплект v3. Компоненты образов/файлов нельзя удалять, пока на них ссылается сохранённое поколение.

Передача IP посетителя исправлена 7 октября: Mac берёт адрес из TCP-соединения и передаёт его через PROXY protocol в Caddy. Два независимых внешних адреса подтвердили отдельные Laravel rate-limit buckets. Caddy заменяет IP-заголовки, а проектный proxy должен доверять только своему предыдущему proxy. При добавлении домена сохранять PROXY listener wrappers и route guard общего ingress; не доверять произвольному клиентскому `X-Forwarded-For`. Подробный контракт — локальный `docs/CLIENT_IP.md`.

Просмотр таймера и списка копий на Mac:

```sh
cd ~/Desktop/CODEX/SERVER
./scripts/serverctl shell sudo systemctl list-timers server-backup.timer --no-pager
./scripts/serverctl shell sudo env BACKUP_CONFIG=/etc/server-backup/offsite.conf /srv/server/deployment/scripts/backup/server-backup.sh snapshots
```

Данные шифруются restic до загрузки. Бюджет серверных копий — 1 ТБ на Google Диске владельца, с сохранением 100 ГБ свободного остатка для личных нужд. Подробный контракт и восстановление: локальный `docs/BACKUP_RESTORE.md`; ключи и Google OAuth параметры хранятся отдельно и здесь не публикуются.

## Документация и координация

Каждый чат ведёт журнал обсуждений/правок и актуальное состояние своего проекта. Общие серверные документы обновляет координатор. Во время параллельной работы назначать отдельные файлы/задачи; не менять общий ingress одновременно. Устаревшие публичные сведения сверять с локальными `AGENTS.md` и `docs/STATUS.md`.

## Границы текущей приёмки

Публичный доступ, TLS, SSH и передача IP проверены. Внешние уведомления об отказе и устаревании backup, полное восстановление размещённых проектов на новом узле, нагрузочный тест и новое испытание удалённого ввода после reboot ещё не приняты. На единственном Mac нет автоматического failover при отказе питания, диска или провайдера. Актуальные проверки и открытые задачи сохраняются в локальном `docs/SERVER_READINESS.md`.
